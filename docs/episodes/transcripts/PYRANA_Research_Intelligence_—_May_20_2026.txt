HOST_A: Okay, today's batch is one of those days where the papers feel like they were written for us. Four of them, and if you squint, they're all asking the same question: how do you keep an agent system from quietly rotting as it grows?
HOST_B: Yeah, that's the through-line. We've got one on formalizing what a "skill" actually is at runtime, one on caching the agent's sense of where it is in a long context, one on what happens when your skill library grows unbounded — spoiler, bad things — and one on the deeper architectural primitive underneath all of it.
HOST_A: And for us, this lands right on two parts of the platform. The @tool decorator — our way of registering capabilities — and the Context Engine, specifically how MessageBuilder hands accumulated knowledge to agents turn after turn.
HOST_B: Right. Two of these four papers are basically draft RFCs for the @tool catalog. One is a draft RFC for MessageBuilder. And the fourth gives us the vocabulary to argue about all of it without waving our hands.
HOST_A: So here's the plan. We walk through them one at a time, plain English first, then we come back and talk about what we actually do this quarter. Because if we read all four and then do nothing, that's the worst outcome.
HOST_B: Agreed. And fair warning — one of these is abstract-only, so we'll be honest when we're guessing versus when we actually have the method.
HOST_A: Let's go. Paper one, Formal Skill.
HOST_B: Okay. Plain English: right now, when people write agent "skills," they basically write a markdown file — a SKILL.md — that tells the model "here's how to do this task, here are the steps, here's what to watch out for." The model reads that prose every time. This paper says: stop doing that. Convert each skill into a structured object with a schema, an executable piece of code, and some governance hooks. The headline result is they hit competitive scores on their benchmark while using about 48% fewer tokens per task.
HOST_A: Forty-eight percent is a lot. What's actually getting compressed?
HOST_B: The prose. Think about a recipe written as a novel versus a recipe written as a checklist with a timer. The novel version has to re-explain every turn what step you're on, what you've already done, what you should avoid. The checklist just has state — "you're on step three, the oven is preheated." The model doesn't need to re-read the novel; it just needs to know what action is available right now.
HOST_A: Okay, explain that like I'm new to this. What's actually in one of these Formal Skills?
HOST_B: Five things. One, a JSON schema — basically a compact description of what actions are available and what arguments they take. Two, a Python executor — actual code that runs the action and validates the arguments. Three, lifecycle hooks — these are intervention points, like "before the model calls this tool, check X" or "before the model says it's done, verify Y." Four, skill-local state — the skill remembers what phase it's in, what's been verified, what artifacts are required. And five, routing metadata so the planner only shows the model the skills that are relevant to the current subtask.
HOST_A: So the runtime is doing the bookkeeping, and the model is just choosing actions.
HOST_B: Exactly. The model reasons, the runtime owns the invariants. That's the split.
HOST_A: What's the catch?
HOST_B: Two things bug me. One, Harness-Bench is their own benchmark. They call it independent, but it was co-developed with their runtime. So we should discount the absolute number a bit. Two, this raises the authoring bar a lot. Writing a SKILL.md is easy. Writing a JSON schema plus a Python executor plus hook logic is real engineering. The paper hand-waves about using an LLM to compile prose into formal components, but they don't actually evaluate that.
HOST_A: So the savings show up at runtime, but the cost shows up at authoring time.
HOST_B: Right. Which means it pays off when a skill gets used a lot — amortization. For PYRANA, the takeaway is: don't formalize everything. Pick our three to five highest-token-cost tools in the context engine and pilot Formal Skill structure there. That's where 48% actually moves the bill.
HOST_A: Good. Paper two — PEEK. This is the abstract-only one.
HOST_B: Yeah, so flag up front: we're working from the abstract. Some of the mechanism is described but the full architecture we don't have.
HOST_A: Got it. Plain English?
HOST_B: When an agent works on a long task — lots of turns, lots of documents — it keeps re-rendering the same orientation information every turn. What's in my context, what entities matter, what schemas am I working with. PEEK says: cache that. Keep a small, fixed-size summary of "where am I" that gets updated as you go, instead of re-deriving it from scratch every turn. They report 6 to 34% improvement on long-context reasoning and somewhere between 93 and 145 fewer iterations versus baselines.
HOST_A: Wait, 93 to 145 fewer iterations is wild. What's an iteration here?
HOST_B: A turn of the agent loop, basically. So instead of the agent thrashing for 200 turns trying to figure out what's going on, it thrashes for 60. That's the claim.
HOST_A: Okay so how does the cache get built and updated?
HOST_B: Three modules. A Distiller that looks at what the agent actually used during inference and extracts the useful orientation signal. A Cartographer that translates that into structured edits to the cached map. And a priority-based Evictor that enforces a fixed token budget — when the map gets too big, evict the lowest-priority entries.
HOST_A: Distiller, Cartographer, Evictor. Cute names. Analogy?
HOST_B: Think of it like a desk. As you work, you keep a sticky-note summary at the top of your desk that says "I'm working on the Q3 contracts, the key parties are A and B, the relevant clause is section 4." Every so often you look at what you've actually been using and you update the sticky note. The sticky note has a fixed size, so when you add something, you pull off the least useful note.
HOST_A: And critically — that sticky note lives in the prompt. It's not a separate retrieval system.
HOST_B: Right, that's the part I want to underline. This isn't another vector database. It's a small structured artifact that rides along in the prompt itself, with an explicit, inspectable update policy. The "programmable" part means the update logic is code we can read, not learned weights.
HOST_A: What's the steel-manned objection?
HOST_B: They evaluate on "recurring same-context workloads" — that's their phrase. So sessions where the agent keeps returning to similar territory. If our agents are doing a lot of one-shot, novel-context work, the Distiller and Evictor are pure overhead with nothing to cache. And the fixed token budget might just be too small for very heterogeneous corpora.
HOST_A: But for long-running PYRANA sessions over a stable corpus, this seems aimed right at our prompt-bloat problem in MessageBuilder.
HOST_B: It does. And the Khattab and Madden co-authorship makes me take it seriously — DSPy and database systems, exactly the right intersection. I'd want to spike a prototype against our longest-running agent sessions and just measure per-turn token reduction.
HOST_A: Okay. Paper three — Library Drift. This is the one that scared me when I read the digest.
HOST_B: It should scare you. Plain English: if you let an agent system add new tools to its own toolbox over time without ever retiring old ones, the system gets worse. Not just plateaus — actively gets worse. And the failure is invisible until it's bad, because aggregate task scores don't reveal it.
HOST_A: How worse?
HOST_B: There's a stat they cite from SkillsBench: LLM-authored skills with no governance produce zero gain over having no skills at all. Human-curated skills give plus sixteen points. The unbounded auto-grown library is literally no better than not having a skill library.
HOST_A: That's a brutal finding. So what's the fix?
HOST_B: Three mechanisms, they call it Ratchet. One, outcome-driven retirement: a skill gets retired once it's been tried at least a hundred times and its contribution score is below negative 0.1. They use Hoeffding bounds — a statistical confidence interval — to make sure they're not retiring on noise. Two, a hard active-cap, default 50 skills. If you'd exceed the cap, the lowest-contributing skill gets evicted. That gives them a formal guarantee the library can't diverge. Three, what they call a meta-skill authoring prior — basically a template that constrains how new skills are written so they're structurally homogeneous and you don't get junk births in the first place.
HOST_A: And of those three, which one matters most?
HOST_B: This is the interesting ablation. Removing the meta-skill — the authoring prior — costs 43% of the total gain. It's the single most valuable component. Stopping bad skills from being born matters more than retiring them after the fact.
HOST_A: Prevention over cure.
HOST_B: Right. And the diagnostic side is just as important. They track per-skill contribution scores, attribution verdicts — helped, hurt, neutral, inapplicable — and router engagement, which is just "what fraction of tasks does the router actually pick a skill for." Healthy is 70 to 80%. In their broken ablation it dropped to 19%. That's a leading indicator. By the time end-task pass-rate moves, you're already in trouble.
HOST_A: Steel-manned objection?
HOST_B: It's all on MBPP+ hard-100 — code generation. Single-call, clear success signal. In our world, a tool gets used as part of a multi-step workflow and attribution is way harder. Did the workflow fail because of the tool, or because of the planner, or because of context? The Critic LLM verdict approach assumes a clean per-injection signal that we mostly don't have.
HOST_A: Fair. But the framework — score, cap, prior — still ports even if the exact metrics don't.
HOST_B: Completely. And here's the thing: our @tool catalog right now has zero of these three mechanisms. No retirement, no cap, no authoring prior. We are exactly the population this paper is warning about.
HOST_A: Okay, last paper. The architecture methodology one — the SDB paper.
HOST_B: This one's the most abstract but maybe the most important. Plain English: every production agent runtime has a moment where a stochastic thing — the LLM — proposes an action, and a deterministic thing — code — has to decide whether to execute it. That boundary is the load-bearing primitive of the whole system. The author calls it the stochastic-deterministic boundary, SDB, and it has four parts: a proposer, a verifier, a commit step, and a reject signal.
HOST_A: Walk me through those four parts.
HOST_B: Proposer is the LLM saying "I want to do X." Verifier is the code that checks whether X is safe and well-formed. Commit is the durable write — the thing that makes the action real. Reject signal is what happens when verification fails: how the system tells the LLM "no, and here's why," in a typed, structured way.
HOST_A: And the claim is that strengthening this boundary matters more over time, not less.
HOST_B: Yeah, and this is the part I love. The author writes down a stylized model: reliability equals architectural momentum times time, plus per-call variance noise. As models get better, per-call variance shrinks. Which means the architectural piece becomes the dominant lever. Pattern choice matters more as models improve, not less.
HOST_A: That's counterintuitive. I'd have guessed better models make architecture less important.
HOST_B: Right, but think about it: if every call is 99.9% reliable, the only failures left are the ones your architecture allows through. The architecture is the ceiling.
HOST_A: What's the evidence beyond the model?
HOST_B: They classified 21 published agent failure post-mortems. 71% localize to SDB weaknesses. 81% of the documented fixes strengthen the verifier, the commit, or the reject signal. And they audited five open-source frameworks and found explicit verifier-and-commit logic at 19 out of 21 LLM-to-action call sites. So this primitive is already everywhere — it just doesn't have a name.
HOST_A: Give me the concrete failure mode that made it click.
HOST_B: The GPT-4o to GPT-4.1 upgrade caused a 23-point drop in prompt-injection resistance — from 94% to 71%. The fix wasn't a new model. The fix was strengthening the verifier. The architecture absorbed the model regression.
HOST_A: And there's this thing called replay divergence that's relevant to Cortex specifically.
HOST_B: Yes — this one I want to dwell on. If you have a deterministic event log, and the consumer of that log is an LLM, then upgrading the LLM changes the downstream behavior even though the log is unchanged. For Cortex, that means CxUs extracted by one model version, consumed by agents running a newer model version, can produce divergent downstream behavior. That looks like a data quality problem but it's actually an architectural one.
HOST_A: Steel-manned objection?
HOST_B: The reliability model is stylized — they admit it. Linear, mean-zero noise, almost certainly wrong in detail. And the six-pattern catalog comes from literature review, not controlled experiments. So treat it as vocabulary and methodology, not as proof.

We should instrument per-tool contribution scoring on a golden replay set this quarter. Cheap to build, immediate signal. Router engagement rate becomes our drift alarm.
HOST_A: And the authoring prior — the meta-skill — connects to the Formal Skill RFC, right? Because if we're going to constrain how new @tools get written, the five-component Formal Skill structure is the spec.
HOST_B: Exactly. Two papers converging on one RFC. Schemas plus executors plus hooks plus skill-local state plus routing metadata becomes the @tool contract, and that same contract is the authoring prior that prevents Library Drift.
HOST_A: Third thing?
HOST_B: PEEK as a Context Engine v2 spike. The Distiller-Cartographer-Evictor pattern over MessageBuilder's accumulated knowledge. Measure per-turn token reduction on our longest sessions.
