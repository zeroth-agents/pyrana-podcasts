But when I lined them up against our roadmap, I realized they all hit different layers of the same stack we're building.
HOST_B: Yeah, it's basically a vertical slice through PYRANA. WorkstreamBench hits the application layer — that's pyrana-demo-2, our financial agent. MOSS hits the harness layer — that's the self-patching thing we've been kicking around. HarnessAPI hits the tool surface — how skills get exposed to both agents and HTTP clients. And LCGuard hits the governance layer — what our audit trail can and can't see.
HOST_A: So if I'm a builder listening to this, the framing is: top to bottom, what's changing this week?
HOST_B: Right. And two of these have actions I'd put on the sprint board today. WorkstreamBench means we should be running our financial agents against it before frontier labs publish numbers we can't match. And HarnessAPI gives us a concrete pattern for closing the gap where our tools are agent-reachable but not HTTP-reachable.
HOST_A: The other two are more medium-term — MOSS is the reference architecture for self-patching whenever we're ready, and LCGuard is a threat we need to document before we ship any KV cache efficiency work.
HOST_B: Exactly. Let's walk them, then come back to what we actually do about it.
HOST_A: Start with WorkstreamBench. Plain English first — what is it?
HOST_B: It's the first transparent benchmark for end-to-end financial spreadsheet construction. The kind of work where you say "build me a discounted cash flow model" and the agent has to produce a multi-sheet Excel workbook with linked formulas. The headline finding is Claude Web — Anthropic's web product — leads all the agents they tested, but even the best ones fall well short of professional finance standards once tasks get complex.
HOST_A: How complex are we talking? Because "build a DCF" could mean a lot of things.
HOST_B: The scale jump is the part that surprised me. The tasks in WorkstreamBench have a mean of about 58,300 cells per task, and a median of 933 function calls. Compared to the previous benchmark in this space, SpreadsheetBench, it's roughly 33 times more cells and 93 times more function calls.
HOST_A: That is a different category of problem.
HOST_B: Completely. And the evaluation is graded on three dimensions — Accuracy, Formula, and Format. So not just "is the final number right" but "are the formulas structured the way a professional modeler would write them" and "does the workbook look right." They use an LLM-as-judge with a fine-grained rubric, validated against expert human annotations.
HOST_A: Wait, back up — LLM-as-judge, that's where you use another language model to grade the agent's output instead of a human?
HOST_B: Right. You give the judge model the reference solution and the agent's attempt, and it returns pass/fail verdicts on each sub-dimension with explanations. The risk is the judge inherits whatever biases the underlying model has. And actually that's the steel-manned objection here — there's another paper in this same digest, AMEL, that directly threatens the reliability of LLM-as-judge evaluations. So that three-dimensional rubric is a great taxonomy, but the scoring methodology has a known soft spot.
HOST_A: And the tasks come from finance competitions, right? Is that representative of real enterprise work?
HOST_B: That's the other objection. They source from Financial Modeling World Cup, ModelOff, and Wall Street Prep — those are stylized "there's a correct answer" problems. Real enterprise finance is much messier, with stakeholder negotiation and ambiguous requirements. So WorkstreamBench is a ceiling on what agents can do on well-defined problems, not a measure of real-world usefulness.
HOST_A: What's the builder takeaway for us?
HOST_B: Two things. One, run pyrana-demo-2 against WorkstreamBench this sprint and publish internal numbers, because we're being benchmarked whether we participate or not. Two — and this is the more interesting one — the Accuracy/Formula/Format taxonomy is a concrete model for how Context Units attached to agent-produced spreadsheets should be structured. Each sub-dimension becomes a verifiable claim with a pass/fail verdict and supporting evidence. That maps almost one-to-one onto a CxU schema for financial artifacts.
HOST_A: So the benchmark doesn't just tell us how we're doing — it tells us how to structure quality claims about agent output. Okay, MOSS next. This is the one I've been most curious about.
HOST_B: Plain English: MOSS is a system that lets an AI agent rewrite its own source code based on its failures, and it actually works on a production-grade codebase, not a toy. The headline number is they took a four-task mean grader score from 0.25 to 0.61 in a single evolution cycle, with no human intervention.
HOST_A: Hold on, that's a huge lift. What does "rewrite its own source code" actually mean here? Is the agent literally editing Python files?
HOST_B: It is. And the distinction that matters is, prior systems in this space — there's Hermes Agent, SkillClaw, EvoAgentX — they only let the agent mutate things like prompts, skill files, or memory. MOSS is the first system that goes all the way down to harness-level code. The thing that wraps the agent and runs it.
HOST_A: That sounds terrifying. How do they keep it from breaking itself?
HOST_B: Seven-stage pipeline with a lot of safety scaffolding. Let me walk it. First, a daemon scans session logs to find failure batches — turns where the agent underperformed, plus turns the user flagged. Then it hands the failure batch and the current source to an external coding agent CLI — could be Claude Code, could be Codex, swappable by config. That coding agent proposes edits.
HOST_A: Okay so far there's a separate AI doing the actual code changes.
HOST_B: Right, MOSS owns the orchestration, the coding agent owns the edits. Then it spins up ephemeral trial workers — N containers built from the candidate image — and replays the failure batch against them autonomously to see if the edits actually fixed the failures. If they do, it asks the user for consent via a CLI exposed to the agent itself. On approval, the host daemon swaps the container in place, runs a health probe, and rolls back automatically if the probe fails. User state lives on a host-mounted volume that survives the swap.
HOST_A: So it's evidence-anchored — it's not just randomly mutating code, it's mutating against specific observed failures.
HOST_B: That's the key differentiator from prior work like Darwin Gödel Machine and SICA, which did source-level self-rewriting but on minimal scaffolds with benchmark-gated exploration. MOSS is directed evolution. Which is what makes it viable on a real codebase instead of a toy.
HOST_A: What's the objection?
HOST_B: Single cycle, single substrate, four tasks. It's a proof of concept, not evidence of stable multi-cycle evolution. The grader isn't independently validated either — so the 0.25 to 0.61 lift could partly reflect the grader rewarding changes that look correct but regress on tasks outside the failure batch. And then the security concern: failure-batch curation is now a high-value attack surface. If you can poison what failures the system sees, you can direct the coding agent to introduce targeted vulnerabilities. The paper doesn't treat that threat extensively.
HOST_A: That's a serious gap. Builder takeaway for PyranaHarness?
HOST_B: MOSS maps almost component-for-component. Our Temporal workflows are their stage machine. Our Langfuse traces are their session JSONL scanning. We already have health probes. Our code interpreter tier is their coding agent CLI. The action is to draft a one-page MOSS-versus-PyranaHarness comparison this sprint and scope a feature-flagged, internal-only self-patching loop. And explicitly threat-model the failure-batch injection attack before any rollout, even internal.
HOST_A: Okay, paper three — HarnessAPI. This one's smaller in scope but very practical.
HOST_B: Right. Plain English: HarnessAPI is a framework where you write one skill — basically a handler plus a Pydantic schema — and it automatically gives you both a streaming HTTP endpoint and an MCP tool from the same source. The headline number is 74% reduction in framework boilerplate compared to maintaining FastAPI and MCP separately.
HOST_A: Pydantic and MCP — for anyone newer, can we unpack those?
HOST_B: Pydantic is a Python library for declaring data shapes — you write a class describing what fields your input has and their types, and you get validation for free. MCP is Model Context Protocol — Anthropic's standard for how agents discover and call tools. So today, if you want a function to be callable both by an agent via MCP and by a human via an HTTP API, you basically write it twice. HarnessAPI says: define it once, get both.
HOST_A: And we already have the agent side via our @tool decorator?
HOST_B: Exactly. We made the same design call — typed skill as the single source of truth. What we don't have is the auto-generated HTTP side. Our tools are agent-reachable but not HTTP-reachable without writing a separate FastAPI route. HarnessAPI shows the clean pattern for closing that.
HOST_A: How does it work mechanically?
HOST_B: They subclass FastAPI and mount FastMCP — the MCP server library — as a sub-application. At startup, a discovery pass walks a skills directory. Each skill folder becomes both an HTTP POST route with content negotiation — JSON or server-sent events streaming based on the Accept header — and an MCP tool registration. Both resolve to the same Pydantic model at runtime, so schema drift between the two transports is structurally impossible rather than convention-enforced.
HOST_A: And there's an access control flag, right?
HOST_B: Yeah, this is the part that's most relevant to us. There's an ismcp flag in the skill config — set it to false and the skill is hidden from MCP but the HTTP endpoint stays live. That maps directly onto our subagentprohibited concept, where some tools are HTTP-reachable for human admins but shouldn't be discoverable by agents.
HOST_A: Objection?
HOST_B: The evaluation is purely boilerplate reduction — cloc line counts across six skills. No end-to-end latency benchmarks, no correctness or concurrency tests. They defer those to future work. And the framework is v0.1.4, so production stability is unproven. The exec-based MCP wrapper and a hot-swap endpoint they include are flagged as security concerns even by the author. For a governed platform like ours, we'd need to harden those before adoption.
HOST_A: But the pattern is the takeaway, not the framework itself.
HOST_B: Right. Builder takeaway: implement a Pydantic-to-OpenAPI emitter this sprint that walks our @tool registry and emits HTTP routes for everything that isn't subagent_prohibited. We don't need to adopt HarnessAPI — we just need the pattern.
HOST_A: Okay, last one — LCGuard. This is the one that genuinely worried me when I read the notes.
HOST_B: Yeah. Plain English: when agents share information between each other, most systems pass text. But there's an efficiency optimization where they share the internal model state directly — specifically the KV cache, which is what the model remembers about the conversation so far. LCGuard's finding is that sensitive content from one agent's input can persist in that shared state and be reconstructable by an adversary, even if it never appears in any text output the system would log.
HOST_A: Wait, can you unpack KV cache? I know we've used the term but for anyone new —
HOST_B: Sure. KV stands for keys and values. When a transformer processes text, at each layer it computes these key and value tensors that represent what it's attended to so far. Normally each call recomputes those from scratch. The cache is just keeping them around so you don't redo that work. The efficiency win is real. The problem LCGuard identifies is that those tensors carry information about the input — and if you ship them between agents, you're shipping that information in a form your audit logs don't see.
HOST_A: So our text-layer audit trail, the Langfuse traces, the CxU lineage — none of that captures what's embedded in representations the agents pass to each other.
HOST_B: That's the uncomfortable finding. They formalize leakage operationally as reconstructability — if an adversarial decoder can recover the original sensitive input from the shared artifact, the artifact is unsafe. They train it as a minimax game: the adversary learns to reconstruct, the system learns a transformation that preserves task performance while making reconstruction fail. They evaluate across Qwen3 at three sizes, Gemma 2, and Llama at two sizes, on three privacy benchmarks — AgentLeak, MAGPIE, PrivacyLens.
HOST_A: And the results?
HOST_B: This is where I have to be honest — the available full text describes results qualitatively as "consistently reduces reconstruction-based leakage" with "competitive task performance," but the specific percentage tables aren't fully reproduced in what we pulled. So we have the framework and the threat model in detail, but not the exact numerical tradeoff. That's a gap.
HOST_A: What's the objection?
HOST_B: The threat model assumes you've actually adopted KV-based latent communication, which most production systems haven't, including us. Today PYRANA subagents communicate via serialized text and structured tool calls. So LCGuard solves a problem we don't have yet.
HOST_A: But the moment we consider any KV reuse efficiency optimization, we have it.
HOST_B: Exactly. Builder takeaway: add KV-cache latent communication as a named threat vector in the subagent dispatch threat model this quarter. Gate any future KV reuse work on a governance review. Don't let inference efficiency get ahead of the audit story.

WorkstreamBench affects pyrana-demo-2 directly — we run our financial agents against it and we use the Accuracy/Formula/Format taxonomy as the CxU quality schema for agent-produced financial artifacts. Each sub-dimension becomes a verifiable claim attached to the artifact, which is exactly the kind of multi-dimensional quality assertion we need.
HOST_A: MOSS is the harness layer.
HOST_B: Right — reference architecture for the self-patching roadmap item. We draft the comparison doc this sprint, scope a feature-flagged internal-only loop, and explicitly threat-model failure-batch injection before anyone touches a production codebase.
HOST_A: HarnessAPI is the tool surface.
HOST_B: The Pydantic-to-OpenAPI emitter is a clear sprint task. Walk the @tool registry, emit HTTP routes for non-subagentprohibited tools, use the ismcp pattern as the model for the access predicate.
HOST_A: And LCGuard is governance.
HOST_B: Documentation action, not implementation. Update the threat model, add the gate. The reason this matters is that all our governance assumes text-layer communication. HOST_A: Field connections — what's the broader trend across these four?
HOST_B: I see two threads.
