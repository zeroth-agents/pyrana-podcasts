HOST_A: Alright, paper one — Data Intelligence Agents, out of C3 AI. Give me the plain-English version.
HOST_B: So this is a production system, not a research demo, that takes a natural language question — "what were our top five accounts by revenue last quarter" — and converts it into a SQL query that actually runs against your database and returns the right answer. The headline result: a single generalist agent matches or beats the best published results on seven different SQL benchmarks, across four different SQL dialects — SQLite, PostgreSQL, Snowflake, DuckDB — with zero fine-tuning. One model, no per-database specialization.
HOST_A: Seven benchmarks is a lot. How are they doing that without specializing?
HOST_B: The trick is they stopped treating the language model as the agent. They wrap it in what they call an Autonomous Coding Agent, or ACA — basically the model plus a sandboxed environment where it can actually execute code and see what comes back. So instead of the model writing a query and hoping it's right, it writes a query, runs it, looks at the result, and checks whether the result matches what the question was asking for.
HOST_A: Wait, back up — how does it know what the result should look like before it's run the query?
HOST_B: Great question, and this is the cleanest part of the design. The Query Generator runs in four phases. Phase one is shape declaration: before writing any SQL, it reads the question and declares, "the answer to this should be a table with these columns and roughly this many rows." Phase two is schema exploration — it sends little probe queries to the live database to confirm, you know, this join key actually exists, this column has the values I think it does. Phase three is generating and running the real query. And phase four is self-verification — it compares the actual result to the shape it declared in phase one. If they don't match, it diagnoses the gap and revises, all in the same pass.
HOST_A: So it's catching its own mistakes before a human or a downstream system sees them.
HOST_B: Exactly. And there's a second piece — a three-tier shared memory. Episodic memory, which is similar past question-and-solution pairs it can pull in. Session lessons, which are rules confirmed on the current database — like "this table's date column is in Unix timestamps not ISO strings." And cross-session lessons, which are rules that generalize across databases. And critically, a cross-session lesson is only written after a live probe query has confirmed its precondition.
HOST_A: Meaning bad lessons can't poison the memory.
HOST_B: Right. The memory is execution-verified before it's allowed to grow. That's the part most multi-agent systems get wrong — they let the agent's beliefs accumulate without checking them.
HOST_A: Okay, steel-man — what's the catch?

HOST_A: Fair. And no published latency or cost-per-query from real deployments.

HOST_A: Okay, paper three — Yale, rubric-conditioned self-distillation. RCSD. Plain English first.
HOST_B: This one is training-time, so it's a little further from our day-to-day, but the insight is what matters. Standard reinforcement learning for reasoning models — the dominant technique is called GRPO — works by having the model generate a bunch of attempts at a problem, scoring each one with a single number, and nudging the model toward higher-scoring attempts. RCSD's argument is that a single number is way too coarse. Instead, you should generate a rubric — a structured checklist of criteria — and supervise the model against the checklist.
HOST_A: And the result?
HOST_B: They beat GRPO by 1.4 points and another recent technique called OPSD by 0.9 points across a science-reasoning benchmark suite, hitting an overall average of 70.6.
HOST_A: Modest gains. How does it work?
HOST_B: Two stages. Stage one — they train a rubric generator. A student model learns to predict, from just the question, what criteria a good answer should satisfy. Each criterion has a title, a description, and a weight — Essential, Important, Optional, or Pitfall. So instead of "this answer is a 7 out of 10," you get "answer must use the correct statistical test — Essential — must not confuse correlation with causation — Pitfall," and so on. Stage two — they use the rubric to give the model fine-grained, token-level feedback on its own reasoning attempts. Correct steps get preserved, specific local errors get penalized.
HOST_A: So GRPO would punish a whole reasoning chain because the final answer was wrong, even if 80% of the steps were fine.
HOST_B: That's the difference. Scalar rewards smear feedback across the whole trajectory. Rubric criteria localize it. And the rubric is only used at training time — at inference the student just sees the question.
HOST_A: Steel-man?
HOST_B: 1.4 points is real but modest, and science reasoning is a domain where rubrics are unusually well-specified. Whether this transfers to open-ended compliance tasks — where the rubric quality itself becomes the bottleneck — is an open question. And there's related work, SD-ZERO and DrTulu, getting comparable gains with simpler mechanisms.
HOST_A: But for us, we don't actually care about the training pipeline.

Each CxU claim gets evaluated against accuracy, source-grounding, compliance-flag, completeness — pass/fail per criterion, with Essential and Pitfall weights. Auditors and downstream agents get criterion-level transparency instead of "quality score: 0.84."
